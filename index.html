01

Repository (repo)

What it is. A project folder whose entire history is tracked by Git. When it lives on a service like GitHub, GitLab, or Bitbucket, other people can see it, clone it, and contribute.

Considerations

  • Add a README.md so future-you (and everyone else) knows what the repo does.
  • Add a .gitignore before your first commit — it's painful to un-track secrets later.
  • Pick a license early if you plan to share it. No license = "all rights reserved."

Resources

  • GitHub Docs — About repositories
  • Pro Git — About version control
  • github/gitignore — starter .gitignore files

02

Clone

What it does. Downloads a full copy of a remote repository — every file, every branch, and the entire commit history — to your machine. After cloning, you have your own working copy connected to the original via a remote called origin.

Considerations

  • SSH clones (git@github.com:…) don't prompt for a password each time; HTTPS often does.
  • Big repos? Use --depth=1 for a shallow clone if you don't need full history.
  • Clone puts things in a new folder named after the repo — cd into it before you run anything.

Resources

  • git-scm.com — git clone
  • GitHub Docs — Cloning a repository
  • GitHub Docs — Connecting with SSH

03

Branch

What it does. Creates a safe, parallel timeline off of the main codebase. Work on a branch until it's ready, then merge it back. main stays green while you experiment.

Considerations

  • Name branches for their intent: feat/onboarding-empty-state, fix/login-typo.
  • Short-lived branches merge cleaner than long-lived ones — rebase or merge often.
  • main is the default in new GitHub repos; older repos may use master.

Resources

  • Pro Git — Branches in a nutshell
  • Atlassian — Using branches
  • Learn Git Branching (interactive)

04

Commit

What it does. A snapshot of your project at a moment in time, plus a short message describing what changed and why. Each commit gets a unique hash and stacks onto the history.

Considerations

  • Write the message for the person reviewing tomorrow — imperative mood: "add empty-state illustration".
  • Small, focused commits are easier to review and to revert.
  • Team using Conventional Commits? Match the format: feat:, fix:, chore:.

Resources

  • Chris Beams — How to write a Git commit message
  • Conventional Commits spec
  • git-scm.com — git commit

05

Push & Pull

What they do. Push uploads your local commits to the remote so teammates can see them. Pull downloads other people's commits and merges them into your branch — it's fetch + merge in one step.

Considerations

  • Pull (or fetch) before you start work so you rebase on the latest, not the stale.
  • First push of a new branch: git push -u origin branch-name to set the upstream once.
  • git pull --rebase keeps history linear instead of creating merge commits.

Resources

  • git-scm.com — git push
  • git-scm.com — git pull
  • Atlassian — Syncing (push, pull, fetch)

06

Fetch

What it does. Downloads new commits and branches from the remote into your local knowledge of it (refs like origin/main) — but doesn't touch your working directory or move your current branch. Think of it as pull minus merge: safe to run anytime.

Considerations

  • Run git fetch before git status to see whether you're behind the remote.
  • After fetching, git log main..origin/main shows exactly what teammates added.
  • Use git fetch --prune to also drop local references to branches that were deleted on the remote.

Resources

  • git-scm.com — git fetch
  • Atlassian — git fetch
  • Julia Evans — How does git fetch work?

07

Diff

What it does. Shows the exact lines that changed between two versions of the code — usually your working copy vs. the last commit, or one branch vs. another. Red = removed, green = added.

Considerations

  • git diff shows unstaged changes; git diff --staged shows what's about to be committed.
  • Large diffs are hard to review — split work into smaller PRs when you can.
  • GitHub's "Files changed" tab is the same diff, rendered with syntax highlighting.

Resources

  • git-scm.com — git diff
  • Difftastic — structural diffing
  • GitHub — Comparing branches

08

Merge

What it does. Combines the work of one branch into another. A "merge commit" ties the two histories together so you can see exactly where a branch joined main.

Considerations

  • Fast-forward merges (no divergence) just move the pointer — no merge commit.
  • Use --no-ff when you want the merge commit for context, even if a fast-forward is possible.
  • If two people touched the same lines, expect a merge conflict (concept #09).

Resources

  • git-scm.com — git merge
  • Atlassian — git merge
  • GitHub — About PR merges (merge, squash, rebase)

09

Rebase

What it does. Takes the commits from your branch, lifts them off, and replays them on top of the latest main as if you'd started fresh. The result is a clean, linear history.

Considerations

  • Rebase rewrites history — never rebase a branch that other people are working on.
  • git rebase -i lets you squash, reword, or reorder commits before merging.
  • If it goes sideways, git rebase --abort gets you safely back where you started.

Resources

  • Pro Git — Rebasing
  • Atlassian — Merging vs. Rebasing
  • GitHub Docs — About git rebase

10

Merge conflict

What it is. Two branches changed the same lines of the same file in different ways, and Git can't decide which one wins. It stops and asks you to pick — or write a hybrid — by hand.

Considerations

  • Look for the conflict markers: <<<<<<<, =======, >>>>>>>. Delete them once resolved.
  • Frequent small merges/rebases mean fewer, smaller conflicts.
  • Editors like VS Code and Cursor have visual "Accept incoming / Accept current / Accept both" buttons.

Resources

  • GitHub Docs — About merge conflicts
  • Pro Git — Advanced merging
  • Atlassian — Resolving merge conflicts

11

Pull Request (PR)

What it is. A GitHub-flavored proposal that says "please review my branch and merge it into main." It bundles the diff, discussion, checks (CI, linters), and approvals in one place.

Considerations

  • A great PR description explains the why, not just the what. Screenshots and before/after help.
  • Keep PRs small enough that a human can review them in ~15 minutes.
  • Draft PRs are for "please look, but don't merge yet." Convert to "Ready for review" when it's… ready.

Resources

  • GitHub Docs — About pull requests
  • GitHub Blog — How to write the perfect PR
  • Google — Code review guidelines

12

Issue

What it is. A ticket for something that needs doing — a bug, a feature, a chore, a question. Issues turn a fuzzy "we should…" into a linkable, assignable, labelable unit of work.

Considerations

  • A good issue has clear steps to reproduce (for bugs) or clear acceptance criteria (for features).
  • Labels (bug, good first issue, design) make triage way faster.
  • Link issues to PRs with "Closes #42" so merging the PR auto-closes the issue.

Resources

  • GitHub Docs — About issues
  • GitHub Docs — Issue templates
  • GitHub Guides — Mastering issues
